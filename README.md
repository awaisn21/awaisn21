## About

I build software that removes manual work from real processes.

I'm an undergraduate at the **Lahore University of Management Sciences**, studying Economics and Mathematics with a minor in Computer Science, and I spend most of my time shipping full-stack products rather than writing coursework code. My engineering centres on **TypeScript and Next.js on the front, PostgreSQL and Supabase underneath**, and increasingly on making language models behave like infrastructure — structured output you can depend on, scheduled background processing, idempotent flows that survive a retry.

The through-line across everything I've built is the same: a process that used to run on spreadsheets, hearsay, or inbox triage now runs on a system. At **Innowi** that meant replacing a 45–90 minute manual quoting workflow with an automated portal that generates signature-ready contracts. With **LUMSight** it meant turning course-selection folklore into a searchable dataset. With **Laveor** it meant designing, building, and operating a commerce storefront end to end as the founder.

Studying economics alongside engineering shapes how I scope work — I think about a feature in terms of the cost it removes and the decision it improves, not just the ticket it closes. That product-engineering instinct is what I bring to a team.

**Open to** — Software Engineering Internships · AI / ML Engineering · Full-Stack Product Roles · Startup & Early-Stage Engineering · Open Source Collaboration

## Featured Projects

<details>
<summary><b>LUMSight</b> — Course & Instructor Review Platform &nbsp;·&nbsp; <code>Vite · React · TypeScript · Supabase</code></summary>

<br />

Course registration at LUMS runs on hearsay. Every enrollment cycle, students scroll through old Facebook threads trying to work out which instructor to take and what a section is actually like. LUMSight replaces that with something searchable — reviews attached to specific instructors and specific course sections, so the comparison takes a minute instead of an evening.

| | |
| :--- | :--- |
| **Role** | Sole builder — designed and built the full platform independently |
| **Stack** | Vite, React, TypeScript, Supabase, Resend (transactional email), Netlify, custom domain |
| **Scale** | 405 seeded reviews across 127 course sections · catalogue reconciliation added 243 courses and 69 instructors · 711 rows of master data |
| **Performance** | Static-first Vite build served from CDN edge; Supabase-backed queries against a normalised, deduplicated course/instructor schema |
| **Security** | Supabase authentication with policy-enforced access; review integrity guarded at the data layer rather than the client |
| **Impact** | Currently in pre-deployment testing, targeting 200 users at launch |
| **Repository** | [lumsight.me](https://lumsight.me/) |

The harder half of this project was never the review form. Before a single review could point at the right thing, the university's course catalogue had to be reconciled into clean master data — courses deduplicated, instructors resolved across inconsistent naming, and sections mapped to the right offering. That reconciliation pass produced 711 rows of trustworthy reference data, and it is the reason a review in LUMSight attaches to a real, specific section rather than a free-text guess.

</details>

<details>
<summary><b>Innowi ISO Partner Portal</b> — Sales & Contract Automation &nbsp;·&nbsp; <code>Next.js 15 · PostgreSQL 17 · Supabase RLS · PandaDoc</code></summary>

<br />

Innowi's point-of-sale partners quoted deals by hand: pricing worked out in a spreadsheet, copied into PandaDoc, sent off and hoped for the best. It took roughly 45–90 minutes per deal, and every step was a chance to paste the wrong number or send the wrong version. I built the internal portal that replaced it.

| | |
| :--- | :--- |
| **Role** | Software Engineering Intern — built the full portal end to end |
| **Stack** | Next.js 15 (App Router, React Server Components, Server Actions), TypeScript (strict), PostgreSQL 17, Supabase (Auth, Storage, Row-Level Security), PandaDoc API + webhooks, Vitest, Playwright, Docker, GitHub Actions, pnpm |
| **Scale** | Multi-tenant partner portal serving Innowi's ISO channel, with per-partner data isolation enforced in the database |
| **Performance** | Manual quoting reduced from ~45–90 minutes per deal to an automated configure-and-approve flow; server-rendered pages with Server Actions removing client round-trips |
| **Security** | Row-Level Security for tenant isolation at the database layer, role-based approval routing, signer controls, and immutable cent-precision price snapshots taken at approval time |
| **Impact** | Replaced spreadsheet quoting with automated pricing, approval routing, and dual signature-ready contract generation — one for the restaurant, one for the partner |
| **Repository** | [isoweb.innowi.com](https://isoweb.innowi.com/login?next=%2F) |

Two decisions define this system. The first is that pricing is snapshotted at cent precision the moment a quote is approved — what a partner signs is provably what was approved, not whatever the pricing table happens to say at signature time. The second is that tenant isolation lives in PostgreSQL Row-Level Security rather than in application code, so a partner cannot read another partner's pipeline even if a query is written incorrectly. Contract generation runs through PandaDoc with webhook-driven state, and the test surface spans Vitest units and Playwright end-to-end flows in CI.

</details>

<details>
<summary><b>Orynto</b> — AI Email Triage & Daily Briefing &nbsp;·&nbsp; <code>Next.js 14 · Prisma · Neon · BullMQ · Groq Llama 3.3 70B</code></summary>

<br />

Orynto is built around the idea that triage is the actual problem, not storage. It connects to a mailbox, classifies what comes in, pulls out deadlines buried in message bodies, and assembles a daily briefing — so the first thing you see each morning is what needs attention, not 200 unread subject lines.

| | |
| :--- | :--- |
| **Role** | Sole builder |
| **Stack** | Next.js 14 (App Router), TypeScript, Prisma + PostgreSQL on Neon, NextAuth v5, BullMQ + Redis on Upstash, Pusher, Stripe, Groq Llama 3.3 70B, shadcn/ui, Tailwind, Zustand, React Query, Recharts, Vercel |
| **Scale** | Gmail and Microsoft Graph integrations built and working; queue-backed processing designed for continuous background sync |
| **Performance** | Inference moved off the request path into BullMQ workers; real-time UI updates pushed over Pusher rather than polled |
| **Security** | OAuth-based mailbox authorisation, environment-scoped secret management, authenticated endpoints, hardened cron routes, and idempotency controls on every write path |
| **Impact** | Pre-revenue and in active development; Stripe billing wired, targeting the first paying user within 60 days |
| **Repository** | `awaisn21/inbox-detox` (private) |

The interesting engineering here is in making an LLM behave like infrastructure. Classification output is constrained to a structured schema and validated before it reaches the database, so a malformed generation is rejected rather than persisted. Background processing runs through BullMQ on Upstash Redis with idempotent job semantics — a retried sync never double-writes a message or duplicates a detected deadline — and scheduled cron routes are authenticated so the processing pipeline cannot be triggered externally.

</details>
